# 性能基准

这份数据由 `scripts/bench.mjs` 生成，可随时重跑。它测的是**端到端**耗时：进程启动、读取文件、解析 BibTeX、扫描 Markdown、生成报告，全部包含在内。

## 环境

| 项 | 值 |
| --- | --- |
| 机器 | Intel Core i7-14700（28 逻辑核）/ 64 GB RAM |
| 系统 | Windows 11（本机） |
| Node.js | v22.23.2 |
| MoonBit | `moon 0.1.20261119`（JS 后端，debug 构建） |
| 命令 | `node _build/js/debug/build/cmd/main/main.js paper.md refs.bib --quiet` |

## 方法

`scripts/bench.mjs` 按规模合成数据集：每个条目 5 个字段、标题里带嵌套花括号；正文每个规模生成同等数量的 `[@key, p. N]` 引用，每 6 行插一个空行模拟真实段落。每个规模跑 3 次，取最小值与平均值。

```bash
moon build --target js
node scripts/bench.mjs            # 默认 100 / 1000 / 5000 / 10000
node scripts/bench.mjs 20000      # 也可以指定规模
```

## 结果（本机实测）

| 文献条目 / 引用数 | BibTeX 体积 | Markdown 体积 | 最小耗时 | 平均耗时 | 退出码 |
| --- | --- | --- | --- | --- | --- |
| 100 | 16.9 KB | 4.7 KB | 49.1 ms | 49.5 ms | 0 |
| 1,000 | 172.4 KB | 48.6 KB | 68.0 ms | 68.8 ms | 0 |
| 5,000 | 879.5 KB | 251.5 KB | 109.9 ms | 113.4 ms | 0 |
| 10,000 | 1.76 MB | 505.1 KB | 167.4 ms | 171.7 ms | 0 |

## 怎么读这组数字

- 100 条的 49 ms 里有大约 45 ms 是 Node 进程启动与模块加载的固定开销，真正的分析只占几毫秒。也就是说，**小项目的耗时几乎全部是启动成本**，这也是「一次检查多个 Markdown」比「逐个文件跑」更划算的原因。
- 从 1,000 到 10,000 条，输入放大了 10 倍，耗时只从 68 ms 涨到 167 ms（约 2.5 倍），增长明显低于线性——固定开销摊薄后，解析与匹配的边际成本大约每条 10 微秒量级。
- 一万条文献 + 一万条引用仍在 200 ms 内完成，说明当前算法（`Map` 建索引 + 未命中才做编辑距离）没有出现平方级退化。真正可能变慢的是「大量未定义引用 + 巨大文献库」，因为每次未命中都要对全库算编辑距离；如果将来遇到这种极端输入，可以给编辑距离加长度剪枝或前缀过滤。
- 以上是 debug 构建。`moon build --target js --release` 会更快，但没有作为基准口径，以免不同机器/构建模式混在一起比较。

## 复现注意

CI 运行在 `ubuntu-latest` 共享 runner 上，绝对耗时会与本机不同，因此 CI 只断言「能跑完且退出码正确」，不设时间阈值——把时间阈值写进 CI 会在共享机器上随机失败，反而降低可信度。
